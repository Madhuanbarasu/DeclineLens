# DeclineLens

**Every declined loan applicant gets the reasons *and* the cheapest path to a yes, computed inside the database, plus an audit of whether that path is equally easy for everyone.**

Built for ExaThon India 2026, Track 01 (Money, Risk & Regulation), on **Exasol Personal**.

## The problem

When a lender declines an application, the customer usually hears nothing useful. Regulators and good practice increasingly expect a clear reason, and customers want to know what they can do about it. Explaining one decision is easy. Doing it for every declined applicant, with a *tested* set of alternatives, and then checking that the help you offer is fair across groups, is a data-scale problem. See [PROBLEM_STATEMENT.md](PROBLEM_STATEMENT.md).

## What it does

| Output | How it is produced |
|---|---|
| **Decision** for every applicant | A transparent logistic model, applied as one SQL expression |
| **Top-3 reasons** per decline | Exact per-feature contribution versus the average approved applicant (window function) |
| **Cheapest path to approval** | ~200 candidate "what if you changed X" plans are cross-joined with every declined applicant, re-scored, and the lowest-effort plans that flip the decision are kept |
| **Customer letter** | Reasons and options in plain language |
| **Fairness audit** | Approval rate, four-fifths impact ratio, share of declined applicants with **no** path to approval, and average effort of the easiest path, by gender / city tier / age band |

The recourse step is the heart of it. For 100,000 declined applicants it evaluates about 20 million what-if scenarios in a single set-based SQL statement ([sql/04_recourse.sql](sql/04_recourse.sql)), which is exactly the kind of wide join-and-aggregate workload an in-memory analytic database is built for.

### A finding the audit surfaces

On the synthetic data, gender is never a model input and the gender gap stays small. But applicants **under 30** have an impact ratio of **0.70** (below the 0.8 screen) and are almost twice as likely to be left with no modelled path to approval (27% vs 15% for ages 45+), because thin credit and employment history act as proxies. Auditing *recourse*, not only approvals, is what makes this visible.

## Architecture

```
generate_applicants (synthetic) --> train logistic model (numpy) --> load into Exasol Personal
                                                                          |
   sql/02_score.sql    score + decide, reference "average approved applicant"
   sql/03_reasons.sql  top-3 reason codes   (UNION ALL + ROW_NUMBER)
   sql/04_recourse.sql applicants x plans   (CROSS JOIN, re-score, keep cheapest 3)
   sql/05_audit.sql    group fairness       (GROUP BY + window MAX)
                                                                          |
                              CLI letters  +  Streamlit dashboard
```

All heavy work (scoring, joins, ranking, audit) runs in SQL inside the database. Python only generates data, fits the small model, and displays results.

## Quick start (Windows PowerShell shown; macOS/Linux commands are the same without the `$env:` syntax)

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

**On Exasol Personal** (the intended platform; see [RUN_GUIDE.md](RUN_GUIDE.md) for setup):

```powershell
$env:EXASOL_DSN = "<host>:<port>"
$env:EXASOL_USER = "<user>"
$env:EXASOL_PASSWORD = "<password>"
python -m declinelens --backend exasol run --rows 200000
python -m declinelens --backend exasol explain          # prints a sample customer letter
$env:BACKEND = "exasol"; streamlit run declinelens/app.py
```

**Try it with no database** (identical SQL on a local DuckDB file):

```powershell
python -m declinelens --backend duckdb run --rows 200000
$env:BACKEND = "duckdb"; streamlit run declinelens/app.py
```

## Correctness

```powershell
pytest -q tests
```

The tests do not just check that code runs:

* SQL scores equal an independent Python implementation for every applicant.
* For 60 declined applicants, a brute-force search over all plans in Python finds the **same cheapest plan** the SQL returned, and applying it really flips the decision. Applicants the SQL calls "no path" are also "no path" in brute force.
* Reason codes are the most negative contributions, in order.
* Protected attributes are provably absent from the model.

## Scale

`python -m declinelens --backend <exasol|duckdb> bench` times the pipeline at 100k, 500k and 1M applicants (up to ~70M what-if evaluations) and writes [docs/BENCHMARK.md](docs/BENCHMARK.md). The committed file holds local DuckDB stand-in numbers; regenerate it on Exasol Personal for your own results.

## Honest limitations

* **All data is synthetic**, generated by [declinelens/data.py](declinelens/data.py). Fairness findings describe the synthetic world, not any real lender.
* The model is deliberately a **simple, readable logistic regression**. That is what makes the reasons exact and the recourse search fast. Richer models (for example gradient boosting scored through a UDF) are a natural extension.
* "Effort" scores for each change are policy inputs a lender would tune. Estimated EMI is `loan / tenure` (no interest) for simplicity.
* Recommended changes are model estimates, not guarantees, and the letter says so.
* Development and automated tests ran on DuckDB, which runs the same SQL files. Run the pipeline once on Exasol Personal before relying on it there.
